# 总目标与分阶段执行计划

更新：2026-09-28。本文是唯一进度与任务入口；规则细节引用规格，测试证据放[验收归档](../archive/README.md)。

## 1. 最终目标与完成标准

交付可在 Monad 测试网完整演示的六工具支付站：Group、Split、Deliver、Attend、Milestones、Rewards，共用账号、工作台、规则预览、操作历史和资金退出入口。

每个工具都要能完成“创建 → 发布 → 执行 → 正常结算或异常退出 → 查询与恢复”，具备中英文、移动端和明确的钱包签名提示。资金以合约为准，网站和数据库不能授予提款权。不扩展到兑换、跨链、发币、借贷、法币通道或平台裁决争议。

完成分两层，不能混记：

1. **工程完成**：六工具代码、合约、页面、API、权限、恢复、必要测试与文档齐全；本地及 CI 验证通过，交付可审阅的 dev→main PR。
2. **发布验收完成**：实际资源隔离、测试网合约登记、真实钱包/设备、外部试用、安全复核和演示证据齐全。主网另经 G-07 授权，不属于默认工程完成。

## 3. 连续执行方式

普通单批请求只完成该批。用户明确授权“全阶段完成”后，按 **M1-C → M2-A → M2-B 工程项 → M3 → M4 → M5 → M6 → M7 工程项** 连续推进；M1-D、真实试用等外部验收可穿插补齐，不阻塞独立工程任务。

每阶段按相同顺序执行：

1. 读取本表、最新文件和远端 dev/main/PR，确认当前任务及影响范围。
2. 按规格先补状态机/合约与必要数据，再接 API、页面、恢复；同阶段形成可演示的完整流程。
3. 运行与改动相关的验证；阶段交付运行完整 CI，修复失败后再推进依赖该阶段的功能。
4. 更新本表、当前操作说明和实际验收记录，提交 dev。已有 dev→main PR 时持续更新同一 PR；用户合并后同步 main，下一批再开 PR。
5. 在全阶段授权内继续下一阶段，不反复等待阶段确认或 PR 合并。最终汇总交付、测试和剩余外部验收；不自动合并。

只有新增且未授权的资源/账户操作、真实签名、主网放行、破坏性数据变更或实质资金规则改变需要用户决定。缺少外部配合时写明依赖和待验证项，继续可独立完成的任务；不能用模拟结果代替真实验收。

效率约定：复用已安装依赖和固定版本工具；每次只读相关规格；日常变更做针对性验证，阶段交付跑全套；不为相同状态重复写报告，不建立未经需要的新目录、框架或通用抽象。

## 4. M1-C：完成 Group 资金闭环

依赖：现有 M1-B 代码与 GroupEscrowV1。先读[资金规则](../product/FUNDS_AND_STATES.md)、[合约规格](../engineering/CONTRACT_SPEC.md)、[Group 说明](../engineering/GROUP.md)。

| 任务 | 交付与完成条件 |
| --- | --- |
| C-01 资金动作与核验 | 类型化接入精确 approve、contribute、leave、finalize、cancel、creditRefund、settle、withdrawFor；每次核对 chain/token/版本/目标/账号/nonce/参数/事件/最终性，禁止支持范围外的账户及交易类型 |
| C-02 参与付款页 | 已发布规则、剩余额度/名额/时间、授权和付款分别确认；授权成功不显示已付款，拒签/revert/未知回执都有明确状态 |
| C-03 退款与结算 | 按角色和链上时间显示退出、取消、退款入 credit、结算及提款；区分可领取款和钱包到账，支持固定受益人退出 |
| C-04 工作台与恢复 | 我创建/我参与/待处理/可领取/历史；刷新、换浏览器、原 hash 与替代交易恢复，禁止 unknown 自动重发，旧证据不得被 RPC 失败覆盖 |
| C-05 数据与回归 | 如需记录参与操作再增加迁移/API；DB 仅保存可核验记录，不作为资金依据。完成下列 GR 验收及完整本地演示 |

验收：GR-01 未达标本金可退、组织者不可提；GR-02 达标但未截止仍可退出并同步人数/locked；GR-03 截止前/等于/后动作唯一、不依赖抢先 finalize；GR-04 满额/重复加入/退出重进/重复退款拒绝；GR-05 READY 且到结算时间才结算；GR-06 取消/结算互斥、退出份额不二次退款；GR-07 暂停新增业务不阻合法退出；GR-08 手机、刷新、拒签、RPC 故障与索引迟到可恢复。

工程完成证据：正常成团、未成团、取消、截止前退出四条流程；每个新资金动作覆盖正常、失败、重复、超时；金额守恒与本地浏览器全流程通过。公众资金开关继续受真实验收约束。

## 6. M2-A：Split 与 Group 组合

依赖：M1-C 的资金动作、credit 和恢复接口稳定。

| 任务 | 交付与完成条件 |
| --- | --- |
| S-01 旧版读取 | 先把部署/订单读取按 chain+address+version 定位，保留 Group V1 查询、恢复和退出；再加入新版本 |
| S-02 分配算法与合约 | 2–20 个固定地址、bps 合计 10000；最大余数整数分配、固定次序处理并列，独立最终付款/nonce/credit/提款 |
| S-03 Split 完整流程 | 草稿、发布、规则预览、付款、个人可领取与恢复；付款前明示不可由付款者强制追回 |
| S-04 Group V2 | 创建时复制冻结分账方案，termsHash 覆盖收款人/比例；成功结算原子分配，失败组只退款，不先转给组织者 |
| S-05 演示与回归 | 同时演示未成团退款、成功 70/30 分账及独立 Split 付款；V1 回归通过 |

验收：SP-01 地址/重复/权重/长度；SP-02 任意整数分配总和守恒、每方误差小于 1 最小单位；SP-03 nonce 不重复；SP-04 单人提款失败不影响他人；SP-05 失败组只退款；SP-06 成功仅分配一次且不可换方案；SP-07 旧版本仍可退出。
